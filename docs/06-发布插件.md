# 06 · 发布插件：npm、GitHub topic 与 awesome 精选列表

> 一句话总结：发布一个插件 = npm publish（token 是关键坑）+ 给仓库打 `dsh-plugin` topic + 向 awesome-dsh-plugin 提一个条目 PR（CI 会检查 bundle 声明、仓库年龄 ≥1 天、提交数 ≥10）；本章给出完整流程与检查清单。

## 1. 发布前检查清单

| # | 检查项 | 要求 | 位置 |
| --- | --- | --- | --- |
| 1 | `dsh.bundle` 声明 | 必须有 `dsh.bundle.patch`（awesome CI 自动检查） | package.json |
| 2 | peerDependencies | 官方 `@deepseek-ai/*` 一律 peer | package.json |
| 3 | `publishConfig.access` | `"public"`（scoped 包必须，否则 publish 报错） | package.json |
| 4 | `files` 白名单 | 只发 `lib`、`cordis.patch.yml`、README 等 | package.json |
| 5 | README | 有 README（含安装、用法、配置表） | 仓库根 |
| 6 | LICENSE | MIT 等 | 仓库根 |
| 7 | 测试 | `node --check` 过、单测过（沙箱里用主模块方式跑） | — |
| 8 | 包名 | 未被占用（`GET registry.npmjs.org/<name>` 返回 404 才可用） | — |
| 9 | 仓库 | 已推 GitHub，≥1 天且 ≥10 commits（awesome CI 硬性要求） | GitHub |
| 10 | topic | 仓库已打 `dsh-plugin` topic | GitHub |

**为什么是这十项？** 前六项保证"这个包是个合格的 npm 包"，第七项保证"代码能跑"，后三项保证"能被生态索引"（npm 不重名、GitHub 有门槛、topic 可被发现）。缺一项，要么发布失败，要么发出去没人能找到。**发布不是终点，能被找到才是**。建议把这张表存成仓库里的 `docs/RELEASE.md`（官方生态插件就是这么做的），每次发布前照着过一遍，比凭记忆可靠得多——漏掉 `publishConfig.access` 这种小字段，发布时才会在最后一步报错，返工成本反而最高。

## 2. npm pack --dry-run：发布前先看内容物

发布前先用 `pack` 预览 tarball 里到底有什么，防止把 node_modules、测试垃圾一起发出去：

```powershell
npm pack --dry-run
```

```bash
npm pack --dry-run
```

**怎么读输出？** 输出会列出将要打包的每个文件及大小。重点核对：

1. `cordis.patch.yml` 和 `lib/` 在不在？**少一个，装了就不生效**；
2. README / LICENSE 在不在？npm 页面上会展示；
3. 有没有不该出现的（`node_modules/`、`.github/`、测试文件）？有就调整 `files` 白名单。

> 小技巧：`npm pack`（不带 --dry-run）会生成一个 `.tgz`，可以解压后逐文件检查，确认无误再删掉。这也是发布前最后一道"眼见为实"的关卡。另外在 pack 之前先确认一件事：**包名在 npm 上是否可用**。浏览器访问 `https://registry.npmjs.org/<你的包名>`，返回 404（JSON 报 not found）说明可用；返回 200 说明被占用，需要改名或加 scope（如 `@你的名字/hello-plugin`）。这一步做晚了，`npm publish` 会直接拒绝。

## 3. npm publish：token 与 2FA

### 3.1 token 类型（403 重灾区）

npm 发布认证靠 token，写在项目根目录的临时 `.npmrc`（记得 gitignore，发布完删除）：

```ini
//registry.npmjs.org/:_authToken=<你的 token>
```

在 npm 官网（npmjs.com → Access Tokens）创建 **granular access token**，关键选项：

| 选项 | 要求 | 否则报错 |
| --- | --- | --- |
| Packages | **All packages**（不能只选某个还不存在的包） | 403 "may not perform that action" |
| Permissions | **Read and write** | 403 |
| **Bypass 2FA for publishing** | **必须勾选** | 403 "2FA required" |

> 三个 403 都是 token 配置问题，不是网络问题，重试无用——回去改 token 选项。**安全提示：** token 不要粘贴到聊天/日志里，放 `$DSH_HOME/secrets/` 之类的本地文件，用完即弃；`.npmrc` 务必进 `.gitignore`。

**拿到一个正确 token 的完整步骤（一次配置，长期受益）：**

1. 打开 npmjs.com → 登录 → 右上角头像 → Access Tokens → Generate New Token；
2. 类型选 **Granular Access Token**；名字随意（如 `dsh-publish`）；
3. Packages 选 **All packages**（注意：如果你先发布了包再想收紧，之后可以再改；但发布前必须 All packages，否则 403）；
4. Permissions 选 **Read and write**；
5. 最关键的：在 **Bypass 2FA** 一栏勾选 `Bypass 2FA for publishing`——这是给 CI/脚本发布用的授权，勾上后发布不再弹 2FA 验证；
6. 生成的 token 只显示一次，立刻复制保存到 `$DSH_HOME/secrets/npm-token.txt`（不要进 git、不要发聊天）。

之后每次发布：把 token 写进临时 `.npmrc` → `npm publish` → 删除 `.npmrc`。可以把这个流程固化成一个脚本（参考官方生态里 `scripts/publish-npm.ps1` 的做法），一次写好，以后一键发布。

### 3.2 执行发布

```powershell
# 先建临时 .npmrc（内容见上），再发布
npm publish --ignore-scripts
```

```bash
npm publish --ignore-scripts
```

- `--ignore-scripts`：跳过生命周期脚本（如 prepublishOnly 里的测试）——沙箱环境常因 npm 子进程被拦截而失败，测试已经在本地手动跑过，这里跳过是安全的；
- 若 npm 缓存路径被沙箱拦截（EPERM），把缓存指到项目内目录：`npm publish --ignore-scripts --cache .npm-cache`；
- 发布成功后可立即验证：`npm view <你的包名> version`。发布失败的常见信号也要会读：403 系列看第 3.1 节的表；`ETARGET` 之类表示版本号问题；网络超时则重试或换镜像。**发布是幂等友好的**：同名同版本会被拒绝（已存在），所以重发时记得先 `npm version patch`。

### 3.3 版本管理

改代码后按 semver 递增版本再发布：

```powershell
npm version patch
npm publish --ignore-scripts
```

```bash
npm version patch
npm publish --ignore-scripts
```

**版本语义建议**：0.x 阶段（0.1.0、0.2.0）随便改，`patch` 修 bug、`minor` 加功能；到了 1.0 之后，`major` 才代表破坏性变更。DSH 官方包目前也是 0.1.0-rc.x 的 pre-release 节奏，跟随即可。

## 4. 给仓库打 dsh-plugin topic

`dsh-plugin` topic 是插件市场的索引标签（可选附加：`deepseek-harness`、`cordis`）。有 GitHub CLI 的话一行搞定：

```powershell
gh repo edit <owner>/<repo> --add-topic dsh-plugin
```

```bash
gh repo edit <owner>/<repo> --add-topic dsh-plugin
```

没有 gh：用 GitHub REST API `PUT /repos/{owner}/{repo}/topics`（或 PATCH 的 `topics` 字段），认证用 classic `repo` token 或 fine-grained token（细节以 GitHub 文档为准）。

**为什么 topic 这么重要？** 它是社区发现插件的第一入口（`github.com/topics/dsh-plugin`），也是 awesome 列表 CI 的检查项之一。打上 topic 后，你的仓库会立刻出现在 topic 页里——相当于给插件挂了"我是 DSH 插件"的招牌。

## 5. 提交 awesome-dsh-plugin PR

`awesome-dsh-plugin` 是官方精选列表仓库，加条目走 PR。流程：

**① fork 并克隆：**

```powershell
# 在 GitHub 网页 fork awesome-dsh-plugin/awesome-dsh-plugin 后：
git clone --depth 1 https://github.com/<你>/awesome-dsh-plugin.git
cd awesome-dsh-plugin
```

```bash
git clone --depth 1 https://github.com/<你>/awesome-dsh-plugin.git
cd awesome-dsh-plugin
```

> 网络不稳时 git 走 schannel 报 TLS 错误？加 `-c http.sslBackend=openssl` 再试，见 [08-常见问题](08-常见问题.md)。

> **如果插件仓库还没推到 GitHub**，先补这一步：`git init -b main` 初始化、提交全部代码、创建远程仓库并推送。没有 gh CLI 时可以用 token 调 REST API 建仓，或用 GitHub 网页手动建空仓库后再 `git remote add origin` 推送。推送若遇 schannel TLS 问题，用 `git -c http.sslBackend=openssl push` 并配合一次性 token URL（推完把 remote 改回干净 URL），详见 08 章。

**② 添加条目：** 新建 `data/plugins/<owner>__<repo>.yml`（**不要手改 README**）：

```yaml
url: https://github.com/<owner>/<repo>
name: <owner>/<repo>
category: memory            # ui | theme | model | session | memory | tools | skill | workflow | notify | dev | market | fun
description:
  en: 'One-line English description ending with a period.'
  zh: 一句话中文描述，以句号结尾。
```

**条目字段逐项说明：**

| 字段 | 说明 |
| --- | --- |
| `url` | 仓库地址，必须真实可访问 |
| `name` | `<owner>/<repo>` 格式 |
| `category` | 十二选一：`ui` `theme` `model` `session` `memory` `tools` `skill` `workflow` `notify` `dev` `market` `fun` |
| `description.en` | 一句话英文描述，**以句号结尾**（CI 可能检查标点） |
| `description.zh` | 一句话中文描述，以句号结尾 |

**③ 生成 README：** awesome 的 README 由脚本从 `data/plugins` 生成，**手改 README 会被 CI 打回**：

```powershell
npm ci
node scripts/generate-readme.mjs --check
```

```bash
npm ci
node scripts/generate-readme.mjs --check
```

先跑 `node scripts/generate-readme.mjs` 重新生成 README，再跑 `--check` 确认同步。生成的 README 会同时出现在 `--check` 比对里，两处一致才算过。

**④ 提交并开 PR：**

```powershell
git checkout -b add/<repo>
git add data/plugins/<owner>__<repo>.yml README.md
git commit -m "add <owner>/<repo>"
git push origin add/<repo>
```

```bash
git checkout -b add/<repo>
git add data/plugins/<owner>__<repo>.yml README.md
git commit -m "add <owner>/<repo>"
git push origin add/<repo>
```

然后在 GitHub 上对上游仓库开 PR：base `main`，head `<你>:add/<repo>`。分支命名用 `add/<repo>` 是惯例，方便维护者一眼看出"这个 PR 加了哪个插件"。

**为什么值得费这个劲提 awesome PR？** 三个理由：其一，`awesome-dsh-plugin` 是官方精选列表，`data/plugins` 已有 1500+ 条目，被收录意味着你的插件进入了“官方认可的生态目录”，用户搜插件时能直接看到你；其二，列表的 README 会为每个条目生成一行描述，等于免费的曝光位；其三，**收录本身就是一次质量背书**——能过 CI 门槛（bundle 声明、≥1 天、≥10 commits、topic）的插件，至少不是三天热度的小玩具。当然，PR 被合并前你可能要等维护者 review，这是社区流程的正常部分。

## 6. CI 会检查什么（以及失败怎么救）

**一次完整的上架时间线（心里有个数）：** 第 0 天：写完插件、本地验证全绿，推 GitHub（此时仓库年龄开始计时）；第 0~1 天：`npm publish` 发布 npm、打 topic；第 1 天以后（仓库满 24 小时、提交数 ≥10）：fork awesome 仓库、加条目、生成 README、开 PR；PR 合并后插件出现在精选列表。**唯一不能压缩的是时间**——age 检查必须等，所以别赶在发布当天就提 PR。

| CI 检查 | 规则 | 失败处理 |
| --- | --- | --- |
| bundle 声明 | 仓库必须声明 `dsh.bundle` | 补 package.json 后重推 |
| 仓库年龄 | ≥ **1 天** | 等满 24 小时后，**在同一分支推空提交**触发重跑：`git commit --allow-empty -m "ci: re-run"`，无需重开 PR |
| 提交数 | ≥ **10 commits** | 补提交（合入更多工作）后重推 |
| topic | 已打 `dsh-plugin` | 打 topic 后重推 |
| README 同步 | 与脚本生成一致 | 重跑 `generate-readme.mjs` 并提交 |

**为什么有年龄和提交数门槛？** 这两个条件过滤"刚建仓就提 PR"的低质量条目，保证列表里的插件至少有真实开发历史。**age 检查失败不是你的代码问题，是时间问题**——等满 24 小时在同一分支推一个空提交触发 CI 重跑即可，规则允许达标后重新提交，没有惩罚，也不用重开 PR。

## 7. 发布后验证（闭环）

```powershell
# 从 npm 装回自己刚发布的插件
dsh plugin --profile web add <你的包名>
dsh --profile web --dump-config | Select-String -Pattern "<你的插件id>"
```

```bash
dsh plugin --profile web add <你的包名>
dsh --profile web --dump-config | grep <你的插件id>
```

装得回来、组合树里看得到、会话里调得动——一条插件就正式加入"一切皆插件"的生态了。**建议发布后 24 小时内在真实会话里完整跑一遍核心功能**：npm 的 tarball 与你本地目录可能有细微差别（`files` 白名单漏文件是最高频事故），只有从 npm 装回来测过才算闭环。具体验证路径：`dsh plugin --profile web add <包名>` 成功 → `--dump-config` 出现组合行 → 会话里让模型调用你的工具并核对返回值 → 再 `dsh plugin remove` 卸载确认清理干净。这套"装 → 查 → 用 → 卸"四步验证，以后每次发布新版本都值得跑一遍。

**本地安装与发布后安装有什么差别？** 本地目录安装（`dsh plugin add <路径>`）时，DSH 直接引用你的源码目录——改代码重启即生效，适合开发。发布后从 npm 安装的是**打包后的 tarball**，只包含 `files` 白名单里的内容，且版本固定。所以：发布前务必 `npm pack --dry-run` 核对内容物，发布后务必从 npm 装回验证——**本地能跑 ≠ 发布后能跑**，`files` 漏文件是最高频的事故类型（比如忘了把 `cordis.patch.yml` 加进白名单，装回来插件直接不生效）。

## 8. 发布后的持续运营

发布不是终点。三条建议让你的插件长期"活着"：

1. **维护 README 与版本节奏**：用户最先看的就是 README，安装命令、配置表、示例一个都不能少；每次功能变更记得 `npm version` 递增；
2. **关注 issue 与 PR**：插件进入生态后会有用户提需求、报 bug，及时响应是口碑的来源；
3. **迭代验证**：每次改完都走一遍"本地目录安装 → dump 验证 → 会话验证 → 发布 → 从 npm 装回验证"的闭环，防止 `files` 白名单漏文件之类的发布事故。

另外可以给仓库加上 `test.yml` / `publish.yml` 之类的 GitHub Actions（官方生态插件的标准配置）：CI 自动跑测试、打 tag 自动发布，人力成本降到最低。
