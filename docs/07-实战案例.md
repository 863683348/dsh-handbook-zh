# 07 · 实战案例：拆解 3 个真实插件的设计

> 一句话总结：从 863683348 插件家族里挑三个代表——`dsh-plugin-focus`（专注板）、`dsh-recipe`（场景配方）、`dsh-gov`（治理套件）——看它们如何把前几章的原则落进代码：三件套结构、纯逻辑分层、schema 先行、ctx.fs 安全、生命周期管理与 fail-safe。

## 1. 三个插件一览

| 插件 | 一句话定位 | 核心工具 | 状态 |
| --- | --- | --- | --- |
| `dsh-plugin-focus` | 给 Agent 一块跨压缩、跨会话存活的"专注板" | `focus`（set/get/append/clear） | ✅ 稳定 + 🧪 实验面板 |
| `dsh-recipe` | "插件界的 dotfiles"：把插件打包成场景配方 | `recipe`（list/search/apply/compose） | ✅ 稳定 |
| `dsh-gov` | 企业配套：权限门禁 + 审计日志 + token 配额 | `gov`（status/policy/audit/quota） | ✅ 稳定 |

三者都已在 npm 发布、仓库打了 `dsh-plugin` topic、进入 awesome 生态，正好是第 06 章流程的活标本。下面逐个拆解：先讲它解决什么问题、怎么用，再讲代码层面怎么设计，最后提炼可复用的模式。

## 2. dsh-plugin-focus：持久化专注板

### 2.1 解决什么问题

Agent 干活时最怕两件事：**上下文被压缩**（compaction）丢掉关键约束，以及**换会话**忘记之前的目标。todo 列表管"下一步做什么"，专注板管"为什么做、什么不能漂移"——目标、硬约束、已做决定。focus 把这些信息持久化到工作区文件里，跨压缩、跨会话存活。

### 2.2 用法（模型侧）

`focus` 工具四个动作：

| action | 参数 | 行为 |
| --- | --- | --- |
| `set` | `note`（必填） | 追加一条"当前焦点/约束" |
| `append` | `note`（必填） | 追加日志条目（决定、发现、反转） |
| `get` | — | 读整块板（最新在前、截断并注明省略数） |
| `clear` | — | 清空；旧板归档到 `.dsh/focus.md.bak`（累积） |

配合提示词段落 `focus:instructions`，模型被教会一套完整用法：任务开始或目标变化时 `set`；工作中 `append` 决定与发现；中断恢复或上下文压缩后 `get` 重读；任务结束 `clear`。

**一个使用场景：** 你在一个大型重构任务里，模型刚说完方案，你告诉它“目标是把迁移做干净，不要动公共接口”。模型调用 `focus set` 把这条记进板子。之后上下文压缩了、甚至你换了个会话继续同一个 workspace，第一步模型就会 `get` 到板子，重新把约束捡回来——这就是“为什么做、什么不能漂移”被持久化的样子。

### 2.3 核心设计

**① 板子是纯文本文件。** 默认 `.dsh/focus.md`，位于会话工作区；条目带时间戳按序排列，`get` 最新在前、按 `maxChars`（默认 8000）截断视图但**永不删文件内容**。文件格式示例：

```text
# Focus Board

<!-- dsh-plugin-focus v1 -->

## [2026-08-14T23:12:00.000Z] set
<note，可多行>

## [2026-08-14T23:13:00.000Z] append
<另一条>
```

**② 自动注入。** 复刻内置 `dsh-time-context` 机制：`agent/pre-step` waterfall 监听器在每轮开始（step 1）以及板子文本变化时，把板子作为 plugin snapshot 消息追加回模型上下文。会话恢复后第一步就能把板子带回来。**板子是工作区级的**：同一 workspace 的新会话能续上旧板子（每个会话从自己的 `session.header.cwd` 解析板子路径）。

**③ `focusBoard` 会话投影。** 每次写入触发 `focus/write` 事件，UI 可用 `useProjection('focusBoard')` 读取；Web 面板（🧪 实验性）经包的 `dsh.client` manifest 在同一组合行上加载 `./client`——"两面一行"：宿主面加载 `.`（工具+注入+投影），浏览器面加载 `./client`（面板）。

**④ 安全。** 所有文件访问走 `ctx.fs`，每个路径解析后都做工作区 containment 校验（`ctx.fs.contains`），板子**永远逃不出工作区**；配置成工作区外路径会 fail loud 报错。

**⑤ 纯逻辑分层。** `lib/board.js` 零 DSH/Cordis 依赖（解析/渲染/变更/归档，`parseBoard`/`renderBoard`/`applyAction`/`buildArchiveText`/`trimEntries`），独立单测；`lib/index.js` 只做接线。

### 2.4 配置表

| 键 | 默认 | 说明 |
| --- | --- | --- |
| `file` | `.dsh/focus.md` | 板文件路径，相对会话工作区；禁止逃逸 |
| `archiveFile` | `.dsh/focus.md.bak` | clear 的归档路径 |
| `archive` | `true` | clear 是否先归档 |
| `maxEntries` | `60` | 磁盘最多保留条目数（最旧丢弃） |
| `maxChars` | `8000` | get / 自动注入的渲染上限（仅视图截断） |
| `autoInject` | `true` | 每轮开始/板子变化时自动注入上下文 |
| `personaSection` | `true` | 注册提示词指引段落 |
| `sectionOrder` | `5` | 提示词段落顺序（persona 为 0，升序） |

**值得学的点：** 板子按"工作区"而非"会话"存放；视图截断不删数据；clear 归档让"清空"可追溯；`autoInject`/`personaSection` 做成可关闭的开关，给使用者留了降级路径。

## 3. dsh-recipe：场景配方（插件界的 dotfiles）

### 3.1 解决什么问题

用户要的是**环境**（"浏览器开发环境"、"学术写作套装"、"通知全家桶"），不是一个一个插件。V2EX 有人做过"插件组合索引"但没做成可安装插件——recipe 把"装一套环境"做进 DSH 本体，一次对话拿到有序插件清单和安装命令。

### 3.2 用法（模型侧）

`recipe` 工具四个动作：

| action | 参数 | 行为 |
| --- | --- | --- |
| `list` | — | 浏览全部配方 |
| `search` | `need` | 按自然语言需求匹配配方 |
| `apply` | `recipeId` 或 `need` | 展开配方：有序插件清单 + 安装命令序列 |
| `compose` | `recipeId`（逗号分隔） | 合并多个配方为整套环境（去重、保序） |

内置 10 个配方：浏览器开发环境（4 插件）、通知全家桶（6）、学术写作套装（5）、移动远程控制（3）、安全加固套装（4）、记忆持久化套装（5）、娱乐休闲（4）、模型路由优化（5）、工作流自动化（5）、插件市场管理（5）。

### 3.3 核心设计

**① 配方格式即数据。** `{ id, name, nameZh, description, descriptionZh, tags, plugins: [{ name, config? }] }`——依赖顺序就是数组顺序；`compose` 做并集去重，天然为 DAG 化编排留了前置。

**② 纯逻辑 + 数据分离。** `lib/recipe.js`（检索/展开/组合/命令序列：`searchRecipes`/`expandRecipe`/`composeRecipes`/`installSequence`）零依赖；`lib/recipe-data.json`（配方）+ `lib/plugins.json`（84 个插件目录，与 dsh-need-finder 同源）。

**③ 零副作用的安全声明。** 无网络、无写入、无 secrets——它只"算"，不"动"。这带来两个好处：核心逻辑极好测（`node test/recipe.test.mjs`），模型可以放心调用（不怕它把环境搞坏）。

**④ 输出即点菜单。** apply/compose 返回 `plugins`（有序清单）+ `commands`（逐条 `dsh plugin add` 命令）+ `oneLine`（一行合并命令），模型可直接执行或交给用户确认。

**值得学的点：** "把环境当数据"——插件的价值可以只是**编排其他插件**；数据（recipe-data.json）与逻辑（recipe.js）分离，新增配方不用改代码。

## 4. dsh-gov：Agent 治理套件（企业级配套）

### 4.1 解决什么问题

企业引入 DSH 时第一波问题永远是三个：**谁能让 Agent 跑高危工具？出事了怎么追溯？钱花哪去了？** gov 把这三件事做成一个插件：策略门禁、结构化审计、token 配额，状态持久化在 `$DSH_HOME/gov/`（全局而非会话，跨工作区一致）。

### 4.2 三大支柱

| 支柱 | 机制 | 数据 |
| --- | --- | --- |
| 策略门禁 | 按工具/agent/工作区规则，allow / deny / ask；`tool` 支持 `*` 通配；`priority` 高者胜，平局 fail-closed（deny > ask > allow） | `gov.json` |
| 审计日志 | 每次工具调用（决定+结果）写入结构化 JSONL（`audit.jsonl`），可查询/导出/汇总 | `audit.jsonl` |
| token 配额 | 接宿主 `tokenMeter`，按 agent 累计用量，周期配额（day/week/month/total），超限注入上下文警告，可一键重置 | `gov.json` |

### 4.3 接线方式（三个事件钩子）

```js
// 1) tools/pre-execute：门禁——命中规则返回 deny/ask，否则放行
ctx.on("tools/pre-execute", async (exec, next) => { /* decide + audit */ });

// 2) tools/result：审计——记录 isError 结果
ctx.on("tools/result", (exec, result) => { /* append audit */ });

// 3) agent/pre-step：计量——ctx.tokenMeter.measure(...)，超限注入警告
ctx.on("agent/pre-step", async (payload, next) => { /* quota */ });
```

`gov` 管理工具（9 个 action）：`status`（总览）、`policy_list/add/remove`（规则）、`audit_query/export`（审计）、`quota_get/set/reset`（配额）。示例：

**一个治理会话示例：** 企业管理员先 `gov policy_add tool="pwsh*" policyAction=ask priority=10` 让所有 shell 命令需要审批，再 `gov quota_set id=alice quotaLimit=100000 period=day` 给 alice 每天十万 token 预算。之后 alice 的 Agent 每次调用 pwsh 相关工具都会先被门禁拦下问询；一旦某天 token 超限，`agent/pre-step` 会在下一轮注入警告。管理者事后用 `gov audit_query decision=deny` 就能看到所有被拒的调用——“谁、什么工具、为什么被拒”一目了然。

```text
gov policy_add tool="pwsh*" policyAction=ask reason="shell 命令需审批" priority=10
gov quota_set id=alice quotaLimit=100000 period=day
gov audit_query decision=deny limit=20
```

### 4.4 设计要点

- **fail-safe**：计量失败、持久化失败都**不阻塞 agent**（catch 兜底，继续放行）；策略引擎平局默认 fail-closed（deny > ask > allow）；
- **审计不含参数内容**：只记工具名、agent、工作区、决定、理由、结果——刻意规避敏感信息落盘；
- **纯逻辑分层**：`lib/policy.js`（规则引擎 `decide`）、`lib/audit.js`（审计模型）、`lib/quota.js`（配额计算）零依赖可单测；`lib/index.js` 只接线；
- **提示词段落教模型**：被 deny 或配额警告**不要绕过**，去找用户调整（`GOV_SECTION_TEXT`）。

**值得学的点：** 治理类插件 = 事件钩子 + 持久化 + 一个管理工具；"默认放行、规则收紧、平局 fail-closed"是平衡可用性与安全的成熟策略；审计日志是纯追加 JSONL，天然可被合规管道消费。

## 5. 三个插件共同的设计模式

| 模式 | focus | recipe | gov |
| --- | --- | --- | --- |
| 三件套结构（package.json + cordis.patch.yml + lib/index.js） | ✅ | ✅ | ✅ |
| 纯逻辑分离（零 DSH/Cordis 依赖的 lib/*.js + 单测） | `board.js` | `recipe.js` | `policy/audit/quota.js` |
| 动作收敛为 `enum` 的参数 schema | `action` 4 值 | `action` 4 值 | `action` 9 值 |
| 规范返回值 + `render` | ✅ | ✅ | ✅ |
| 文件安全（`ctx.fs` + containment） | ✅（工作区） | 无文件（只算） | ✅（`$DSH_HOME/gov`） |
| 生命周期管理（`ctx.effect` / `ctx.on`） | ✅ | ✅ | ✅（3 个钩子） |
| fail-safe（失败不拖垮 Agent） | ✅ | ✅（零副作用） | ✅（明确声明） |
| 配置可开关（降级路径） | ✅（autoInject 等） | 少（sectionOrder） | ✅（prestepWarn 等） |

**给新手的三个取经结论：**

1. **先分离纯逻辑**：把"解析/计算/渲染"写成不依赖 DSH 的函数，你就能在没有 DSH 的测试环境里把核心逻辑测到绿——三个插件全部如此，你的第一个插件也应该如此；
2. **schema 先于实现**：把 `parameters`、`output.schema` 当接口契约先定死，实现只是填空；动作一律 `enum`，模型才调得准；
3. **安全是默认项**：能碰文件就做 containment 校验，能碰钱（token）就做配额与审计，能做失败兜底就 fail-safe——这三个插件把"不出事"设计成了默认行为。

**怎么"抄作业"？** 每个插件的仓库都是现成教材，建议按这个顺序读：`README.md`（定位与用法）→ `cordis.patch.yml`（组合行与默认配置）→ `lib/index.js`（接线）→ `lib/*.js`（纯逻辑）→ `test/*.test.mjs`（测试怎么写的）。看完照着写一遍，比任何教程都管用。

## 6. 本章小结

**三个插件三句话：** focus 把"上下文工程"做成了持久化文件 + 自动注入；recipe 把"环境编排"做成了纯数据 + 纯逻辑；gov 把"企业治理"做成了钩子 + 持久化 + 管理工具。它们的共性不是代码多漂亮，而是**每一条都踩在前几章的原则上**：三件套结构让它们可安装，纯逻辑分层让它们可测试，schema 先行让模型调得准，containment 与 fail-safe 让它们出不了大事。

**给你的一句话行动建议：** 读完本章后，去 GitHub 打开这三个仓库之一（推荐从 `dsh-plugin-focus` 开始），按 05 节建议的顺序读一遍源码，然后动手实现一个 20 行以内的小工具插件——等你亲手跑通 `--dump-config` 看到自己插件的组合行那一刻，DSH 插件开发对你就不再是"教程里的概念"，而是"手上的工具"了。

`focus` 展示了"持久化 + 注入"的上下文工程，`recipe` 展示了"插件编排插件"的数据化思维，`gov` 展示了"钩子 + 持久化 + 管理工具"的治理结构。三者共同验证了本书前六章的每一条原则都可以落地。下一章 [08-常见问题](08-常见问题.md) 是踩坑速查表——Windows 路径、沙箱 EPERM、npm 403、git TLS……写插件路上会遇到的坑都在那里。
