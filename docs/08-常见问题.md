# 08 · 常见问题：踩坑速查表

> 一句话总结：本章把 DSH 开发中最常踩的坑按"症状 → 原因 → 处理"整理成速查表——Windows 路径引号、沙箱 EPERM、npm 403、git TLS、awesome CI 年龄检查、PowerShell 转义、ctx.fs 权限——遇到先查表，别自己瞎试。

## 1. 踩坑速查总表

| 症状 | 原因 | 一句话处理 |
| --- | --- | --- |
| PowerShell 里路径带 `'`（如用户目录 `l'x`）报错 | 单引号字符串被路径里的引号截断 | 单引号写成 `''`（两个单引号）或改用双引号 |
| `node --test` 报 EPERM / 子进程被拦截 | 沙箱拦子进程管道 | 改主模块方式跑测试文件：`node test\xxx.test.mjs` |
| npm 403 `2FA required` | 用了 classic token + 2FA | granular token 并勾选 **Bypass 2FA for publishing** |
| npm 403 `may not perform that action` | granular token 只选了 select packages | 换成 **All packages** 的 token |
| npm EPERM 缓存路径 | 沙箱拦 `AppData\npm-cache` | 加 `--cache <项目>/.npm-cache` |
| git 克隆/推送报 TLS/schannel 错误 | 网络环境证书问题 | `-c http.sslBackend=openssl` |
| awesome CI 的 age 检查失败 | 仓库创建不满 1 天 | 满 24h 后在原分支推空提交重跑 |
| 插件路径"逃逸工作区"报错 | 配置路径在工作区外 | 改为相对工作区的路径；文件读写走 `ctx.fs` |
| PowerShell 命令里 `$`、引号行为怪异 | 变量展开与转义 | 用反引号转义（PowerShell）或单引号字符串 |
| `--dump-config` 输出中文乱码 | PowerShell 重定向默认编码 | 用 `Out-File -Encoding utf8` |
| 模型"看不到"新装的工具 | 没重启，或 description 太含糊 | 重启 DSH；把工具描述写具体 |

下面逐项展开。

## 2. Windows 路径里的单引号（`l'x` 之类）

**症状：** 路径含单引号时 PowerShell 报"字符串缺少终止符"或路径解析错误。典型例子：用户目录 `C:\Users\l'x\...`。

**原因：** PowerShell 单引号字符串里再出现单引号会提前终止字符串。

**处理：** 把路径里的单引号写成**两个单引号**（`''` 是 PowerShell 转义单引号的写法），或整个字符串改用双引号：

```powershell
# 错误：字符串被 l'x 的引号截断
cd 'C:\Users\l'x\WorkBuddy\demo'

# 正确 1：单引号写成两个
cd 'C:\Users\l''x\WorkBuddy\demo'

# 正确 2：用双引号包（注意 $ 会被展开，路径里没有 $ 就安全）
cd "C:\Users\l'x\WorkBuddy\demo"
```

```bash
# bash：单引号里不能转义单引号，改用双引号或拼接
cd "/c/Users/l'x/WorkBuddy/demo"
cd '/c/Users/l'"'"'x/WorkBuddy/demo'
```

> 在 Node/JS 代码里遇到这种路径则没有这个问题，字符串字面量照常写。**预防建议：** 给项目建一个不含单引号的短路径（如 `D:\dev\<项目>`），从源头避免这类转义地狱。

**同类问题：PowerShell 重定向中文乱码。** `dsh --profile web --dump-config > dump.yml` 在 Windows PowerShell（5.x）里默认用 UTF-16 写文件，内容打开变乱码，bash 则没这个问题。统一用 `Out-File -Encoding utf8` 解决（08 章的转义对照表里也列了这条）。

## 3. 沙箱 EPERM：node --test 的子进程被拦截

**症状：** 在受限环境（CI 沙箱、DSH 自身的文件沙箱）跑 `node --test test/` 报 EPERM，或提示子进程管道被拒绝。

**原因：** 沙箱禁止通过管道捕获子进程输出（`node --test` 会 spawn 子进程），这是设计好的边界，不是 bug——**不要反复重试同一命令**，改用法。

**处理：** 改用**主模块方式**直接跑测试文件（`node:test` 文件本身可以当主模块执行）：

```powershell
# 不要用：node --test test/
node --check lib\index.js
node test\board.test.mjs
node test\recipe.test.mjs
```

```bash
node --check lib/index.js
node test/board.test.mjs
node test/recipe.test.mjs
```

发布时同理：`npm publish --ignore-scripts`（测试已在本地手动验证），避免 npm 生命周期脚本在沙箱里触发子进程。

**相关症状：模型“看不到”新装的工具。** 装了插件、dump 里也有，但模型就是不用。先查两件事：第一，**重启了没有**——配置树在启动时组合，运行中的会话不会加载新插件；第二，**工具描述（description）够不够具体**——“提供 focus 功能”这种描述模型不知道怎么触发，改成“当需要记录任务目标/约束/决定时调用”这类“何时用”的表述。05 章讲过：description 是模型的说明书。

## 4. npm 403

npm 发布 403 基本都不是网络问题，重试无效。按错误信息对号入座：

| 错误信息 | 原因 | 处理 |
| --- | --- | --- |
| `403 2FA required` | token 没被授予跳过 2FA 的权限 | 建 token 时勾选 **Bypass 2FA for publishing** |
| `403 may not perform that action` | granular token 只授权了 select packages，而目标包不存在/不在清单 | 换成 **All packages** 范围 |
| `403 You must be logged in` | token 没写进 `.npmrc` 或格式不对 | 确认 `//registry.npmjs.org/:_authToken=<token>` |

**推荐配置：** npm 官网创建 **granular access token**：Packages = All packages，Permissions = Read and write，勾选 Bypass 2FA for publishing。token 放本地文件（如 `$DSH_HOME/secrets/npm-token.txt`），**不要粘贴到聊天记录或提交进 git**。

**验证是否解决：** 改完 token 后重新执行 `npm publish`，若仍 403 则去 npmjs.com 的 Access Tokens 页面核对勾选项——最常见的坑是忘了勾 Bypass 2FA。

## 5. npm EPERM 缓存路径

**症状：** 发布或安装时报 `EPERM ... npm-cache`。

**原因：** 沙箱拦截了默认缓存目录（Windows 上 `AppData\npm-cache`）。

**处理：** 把缓存指到项目内目录：

```powershell
npm publish --ignore-scripts --cache .npm-cache
```

```bash
npm publish --ignore-scripts --cache .npm-cache
```

（`.npm-cache` 记得加进 `.gitignore`。）这条对 install/pack/publish 都适用，沙箱里跑 npm 相关命令时养成加 `--cache` 的习惯。

## 6. git schannel TLS 失败

**症状：** `git clone` / `push` 报证书/TLS 错误（Windows 上常见：curl schannel 校验失败）。

**原因：** 网络环境/系统证书问题导致 Windows 默认的 schannel 后端握手失败。

**处理：** 强制改用 OpenSSL 后端：

```powershell
git -c http.sslBackend=openssl clone https://github.com/<owner>/<repo>.git
git -c http.sslBackend=openssl push origin <branch>
```

```bash
git -c http.sslBackend=openssl clone https://github.com/<owner>/<repo>.git
```

极少数情况下还需要配合一次性 token URL 推送（推完把 remote 改回干净 URL）。**预防建议：** 一次性命令成功后，可以 `git config --global http.sslBackend openssl` 固定后端，避免每条命令都带参数。

## 7. awesome-dsh-plugin CI 的 age 检查失败

**症状：** PR 的 CI 报"repository must be at least 1 day old"（或 commits 不足）。

**原因：** awesome 列表的三条硬性规则：必须声明 `dsh.bundle`（自动检查）、仓库 ≥ **1 天** 且 ≥ **10 commits**、已打 `dsh-plugin` topic。刚建仓立刻提 PR 必挂。

**处理：**

- 提交数不足 → 把真实工作合入仓库（≥10 commits）后重推；
- 年龄不足 → **等满 24 小时**，然后**在同一分支推空提交**触发 CI 重跑，**无需重开 PR**：

```powershell
git commit --allow-empty -m "ci: re-run"
git push
```

```bash
git commit --allow-empty -m "ci: re-run"
git push
```

规则允许达标后重新提交，没有惩罚。**心态提示：** age 失败是时间问题不是质量问题，别为它熬夜，设个 24 小时的提醒即可。

## 8. PowerShell 路径与命令转义

PowerShell 与 bash 的转义规则不同，常见差异：

| 场景 | PowerShell | bash |
| --- | --- | --- |
| 字符串里嵌双引号 | 外层用单引号 | 转义 \" 或外层单引号 |
| 字符串里嵌单引号 | 写两个 `''` | 双引号包住 |
| 变量 | `$env:NAME`（环境变量） | `$NAME` |
| 特殊字符（如 `$`） | 用反引号转义 | 用反斜杠转义 |
| 输出重定向到文件 | `Out-File -Encoding utf8`（避免中文乱码） | `>` |

例如保存 `--dump-config` 输出：

```powershell
dsh --profile web --dump-config | Out-File -FilePath dump.yml -Encoding utf8
```

```bash
dsh --profile web --dump-config > dump.yml
```

**一句话记法：** PowerShell 的转义字符是**反引号**，bash 的转义字符是**反斜杠**；PowerShell 里变量用 `$env:NAME` 读环境变量。搞混了就去对照表，别硬背。

**路径书写的一个统一约定（少踩一半坑）：** 在给读者/文档写命令时，Windows 命令里用反斜杠（`lib\index.js`），bash 里用正斜杠（`lib/index.js`）；但在 **Node/JS 代码里**（插件源码、测试），一律用正斜杠或 `node:path` 的 `join`——因为 JS 字符串里的反斜杠是转义符，`'lib\index.js'` 会变成 `libindex.js` 之类的鬼东西。这条规则记住，Windows 相关转义问题直接少一半。

**PowerShell 执行策略（偶尔碰到）：** 跑 `ps1` 脚本（比如发布脚本）报"禁止运行脚本"，是执行策略限制。查看 `Get-ExecutionPolicy`，临时放行用 `Set-ExecutionPolicy -Scope Process Bypass`（只影响当前窗口）。这是 PowerShell 通用知识，不是 DSH 特有，但写插件发布脚本时会遇到。

**WSL 用户的提示：** WSL 里 dsh 与 npm 都按 Linux 方式工作（`~/.dsh`、正斜杠路径），Windows 侧的坑基本不沾；但注意 WSL 与 Windows 的文件系统互访（`/mnt/c/...`）会让路径很长，建议在 WSL 自己的文件系统里建项目。

**常见启动问题速答：**

- **端口被占用**：`dsh web` 起不来，终端报 EADDRINUSE → 换端口：`dsh --profile web --port 8080`；
- **profile 不存在**：`dsh --profile mydev` 报错 → 自定义 profile 必须先用 `dsh plugin --profile mydev ...` 创建（web/headless 才自动初始化）；
- **改了配置没生效**：先 `--dump-config` 确认值，再确认改对了文件（profile 级 vs home 级），最后确认重启了。

## 9. ctx.fs 权限与 containment

**症状：** 插件报 `escapes the session workspace`，或读写被拒。

**原因与规则：**

- **插件文件读写必须走宿主 `ctx.fs`**（`resolve` / `stat` / `readText` / `writeText` / `contains`），不要直接 `node:fs`；
- 配置路径解析后必须过 `ctx.fs.contains` 工作区校验——配置成工作区外路径会 fail loud（刻意设计，见 05 章）；
- `exec.agent.session.header.cwd` 是会话工作区，路径以它为基准；
- 全局数据（如 dsh-gov 的 `$DSH_HOME/gov`）走 `dshHomePath` 之类的宿主能力，不要硬编码拼接。

**排查顺序：** ① 是不是直接用了 `node:fs` → 改走 `ctx.fs`；② 路径是否相对工作区 → 改成相对路径；③ 是否越权写 `$DSH_HOME` 之外 → 用宿主提供的 home 路径能力。仍不确定的以官方文档为准。

## 10. 调试三板斧

**三板斧的顺序是有道理的：** 先确认"配置层没问题"（1），再确认"代码层没问题"（2），最后才是"运行时行为"（3）——按这个顺序排查，80% 的插件问题能在前三分钟定位。

**一个完整的排查示例（照着练）：** 你刚写完插件，`dsh plugin add` 成功，但会话里模型说没有你的工具。按三板斧走：① `--dump-config | Select-String <你的id>`——没有输出？先查 `cordis.patch.yml` 的 `insert` 缩进和 `id`/`name` 一致性；② 有输出但模型还是看不到？`node --check lib\index.js` 过不过、`inject` 里声明的服务有没有写全、`apply` 有没有真的调用 `ctx.tools.register`；③ 都正常？重启后直接在会话里命令模型"调用 xxx 工具"，看它报什么错——工具调用失败的错误信息会直接暴露问题点。

**怎么向别人求助（带上这三样）：** ① 你的 `--dump-config` 输出（截取相关片段）；② `node --check` 结果与插件目录结构；③ 会话里模型调用工具时的报错原文。这三样齐了，任何熟悉 DSH 的人都能快速定位——比一句"我的插件不生效"有效一百倍。

遇到任何"插件没生效/行为怪异"，按顺序做：

1. **看组合树**：`dsh --profile <name> --dump-config`——插件行在不在？config 对不对？
2. **看语法**：`node --check lib\index.js`——语法错会在这里现形；
3. **看会话行为**：重启后在会话里让模型调用该工具，观察返回的规范值与错误信息。

**三板斧的顺序是有道理的：** 先确认"配置层没问题"（1），再确认"代码层没问题"（2），最后才是"运行时行为"（3）——按这个顺序排查，80% 的插件问题能在前三分钟定位。

**速查表的使用姿势：** 别等出事了才翻——把第一章的“新手检查清单”和本章的总表各打印/收藏一份，每次装插件、写插件、发插件之前先过一眼。坑是踩不完的，但**高频的坑就这几类**，覆盖了它们，你的 DSH 之旅会顺畅得多。
