# 04 · 写第一个插件：三件套骨架与 hello 工具

> 一句话总结：一个可安装的 DSH 插件只有三个文件——`package.json`（声明"我是组合包"）、`cordis.patch.yml`（把自己插入组合树）、`lib/index.js`（Cordis 插件本体），本章逐个文件拆解并写一个最小可运行的 `hello` 插件，装进本地 profile 验证。

## 1. 先建立正确的心智

写插件前先想清楚一个模型：**插件 = 组合包 + 代码**。

- **组合包（bundle）**：负责"进配置树"。`package.json` 里的 `dsh.bundle.patch` 声明"我的补丁是哪个文件"，`cordis.patch.yml` 里的 `insert` 把自己追加进组合列表——这一步决定了插件会不会被加载；
- **代码**：负责"提供能力"。`lib/index.js` 是一个标准的 Cordis 插件，在 `apply(ctx, config)` 里注册工具、注入提示词、挂生命周期钩子。

第 02 章讲过配置叠加：组合包的 patch 是第 1 层。所以你的插件装进 profile 后，它的 patch 会参与叠加，你的工具就出现在 Agent 的工具列表里了。本章用最小例子走通这条链路。

三件套总览：

| 文件 | 内容 | 一句话职责 |
| --- | --- | --- |
| `package.json` | `dsh.bundle.patch` 指向 `cordis.patch.yml` + peerDependencies + `publishConfig.access: public` | 声明"这是一个 DSH 插件组合包" |
| `cordis.patch.yml` | `insert` 组合补丁 | 把自己（一行组合行）插进组合树 |
| `lib/index.js` | Cordis 插件：导出 `{ name, inject, Config, apply }` | 实际注册工具、注入提示词、管理生命周期 |

目录结构：

```text
hello-plugin/
├── package.json
├── cordis.patch.yml
└── lib/
    └── index.js
```

下面把 `hello-plugin` 写出来：它注册一个 `hello` 工具，向模型提供"打招呼 + 汇报当前工作区"的能力。

## 2. package.json：插件的身份声明

```json
{
  "name": "hello-plugin",
  "version": "0.1.0",
  "description": "第一个 DSH 插件：注册一个 hello 工具",
  "type": "module",
  "main": "lib/index.js",
  "files": ["lib", "cordis.patch.yml", "README.md"],
  "license": "MIT",
  "publishConfig": { "access": "public" },
  "dsh": { "bundle": { "patch": "./cordis.patch.yml" } },
  "peerDependencies": {
    "@deepseek-ai/cordis": "^4.0.1",
    "@deepseek-ai/dsh-fs": "^0.1.0-rc.6",
    "@deepseek-ai/dsh-system-prompt": "^0.1.0-rc.6",
    "@deepseek-ai/dsh-tools": "^0.1.0-rc.6",
    "@deepseek-ai/schemastery": "^3.18.1"
  }
}
```

逐字段要点：

| 字段 | 说明 |
| --- | --- |
| `name` | 包名，npm 上唯一；发布后用户用这个名字安装 |
| `version` | 语义化版本，发布流程（06 章）会递增 |
| `type: "module"` | 插件用 ESM 编写（与 DSH 一致，`import`/`export` 语法） |
| `main` | 指向 Cordis 插件入口 `lib/index.js` |
| `files` | 发布进 npm 包的文件白名单（只发该发的，别把测试和 node_modules 发出去） |
| `dsh.bundle.patch` | **核心**：告诉 DSH"我的组合补丁是 ./cordis.patch.yml"，有此声明才被识别为插件组合包；awesome 列表的 CI 也会自动检查这一项 |
| `publishConfig.access: public` | 发布到 npm 时公开访问（scoped 包不写会发布失败；发布章节细讲） |
| `peerDependencies` | 官方 `@deepseek-ai/*` 运行时一律放 peerDependencies，由宿主提供，插件不重复安装 |

> 为什么官方包用 peerDependencies？因为 DSH 宿主（profile 运行时）已经装载了 `dsh-tools`、`dsh-fs`、`dsh-system-prompt` 等，插件直接复用同一份，避免版本分裂；如果每个插件都自己 `npm install` 一份，装两个插件就可能出现两份不同版本的运行时，互相打架。**这个习惯不要破坏。** 需要用到的服务对应关系（`dsh-tools` → `ctx.tools`、`dsh-fs` → `ctx.fs`、`dsh-system-prompt` → `ctx.systemPrompt`）在 05 章展开。

**装好之后，DSH 启动时对它会做什么？** 走一遍这个链路，你对三件套的理解会更深：启动时，DSH 读取 `dsh.profile` 的 bundles 列表 → 找到你的组合包 → 读 `package.json` 的 `dsh.bundle.patch` 找到 `cordis.patch.yml` → 执行其中的 `insert` 把组合行加进配置树 → 运行时按 `name` 字段解析包 → 加载 `main`（`lib/index.js`）→ 校验 `inject` 声明的服务是否就绪 → 校验 `Config` 并合并 `config` → 调用 `apply(ctx, config)`。**任何一个环节出问题，插件都起不来**——排查插件问题时按这条链路倒着查。

## 3. cordis.patch.yml：把自己插进组合树

```yaml
# Bundle patch layer：launcher 组合从空列表开始，所以这里的补丁都是 insert
- insert:
    - id: hello
      name: 'hello-plugin'
      config:
        greeting: '你好，我是第一个 DSH 插件！'
```

- `insert`：往组合列表里**追加一行组合行**。回忆 02 章，profile 的配置树从空根开始叠加 patch，因此这里用 `insert` 而不是修改既有行——**launcher 组合从空列表开始，每个组合包都只负责 append**，这就是插件能任意组合的根基；
- `id`：组合行唯一标识（如 `hello`），也是插件的 Cordis 名字，**必须与 `lib/index.js` 里导出的 `name` 一致**；
- `name`：包名（`'hello-plugin'`），运行时从这里解析插件实现；
- `config`：传给插件 `Config` 的配置对象（可省略，用默认值）。字段名与 `Config` 里定义的对齐，缺省字段自动取默认值。

> 动手验证：改改 `greeting` 的值，重启后 `hello` 工具的问候语会跟着变——这就是"配置驱动行为"的最小演示。

## 4. lib/index.js：Cordis 插件本体

```js
// hello-plugin/lib/index.js
import z from "@deepseek-ai/schemastery";
import { defineTool } from "@deepseek-ai/dsh-tools";

/** Cordis 插件名（与组合行 id 一致）。 */
const name = "hello";

/** 本插件依赖的宿主服务，全部就绪后才会 apply。 */
const inject = ["tools", "systemPrompt"];

/** 组合行 config 的校验/默认值 schema。 */
const Config = z.object({
  greeting: z.string().default("你好，我是第一个 DSH 插件！"),
});

function apply(ctx, config) {
  // 1) 注册模型工具
  ctx.tools.register(defineTool({
    name: "hello",
    description: "向用户打招呼，并汇报当前会话的工作区路径。",
    parameters: {
      name: { type: "string", required: true, description: "要打招呼的对象名字。" },
    },
    output: {
      schema: {
        type: "object",
        additionalProperties: false,
        required: true,
        properties: {
          message: { type: "string", required: true },
        },
      },
      render: (_args, value) => [{ type: "text", text: value.message }],
    },
    execute: async (args, exec) => {
      const cwd = exec.agent?.session?.header?.cwd; // 会话工作区
      return { message: config.greeting + " " + args.name + "（工作区：" + (cwd ?? "未知") + "）" };
    },
    presentCall: (args) => ({ card: "generic", title: "Hello " + args.name, kind: "other", rawInput: args }),
  }));

  // 2) 注入一段提示词，教模型什么时候用 hello
  ctx.effect(() => ctx.systemPrompt.section({
    name: "hello:instructions",
    order: 5,
    text: "当用户想测试插件是否工作时，调用 hello 工具。",
  }), "hello.section()");
}

export { Config, apply, inject, name };
```

**导出结构拆解（四个导出缺一不可）：**

| 导出 | 作用 | 关键点 |
| --- | --- | --- |
| `name` | 插件名字符串，加载器用它注册 | 须与组合行 `id` 一致 |
| `inject` | 依赖的宿主服务数组 | 声明了才能用：`tools`、`systemPrompt`、`fs`、`agents` 等 |
| `Config` | 用 schemastery（`z.object`）描述配置 schema | 缺省值在这里给，`config` 传进来时已校验 |
| `apply(ctx, config)` | 插件主体 | 注册工具、注入提示词、挂钩子都在这 |

**apply 内部逐行看：**

再看 `Config` 的写法：`z.object({...})` 来自官方 `@deepseek-ai/schemastery`。它做的事是"声明配置的形状 + 给默认值"：`z.string().default("...")` 表示该字段是字符串、缺省时用默认值。宿主会拿着组合行 `config` 来校验并补全，`apply` 收到的 `config` 一定是"形状正确、缺省已补"的——所以你的代码里可以放心地直接用 `config.greeting`，不用写任何防御性判断。这与 05 章的工具参数 JSON Schema 是两套体系（配置用 schemastery，工具参数用 JSON Schema），别搞混。

**为什么 `Config` 校验值得认真写？** 因为组合行的 `config` 来自 `cordis.patch.yml`，而那个文件是**用户手写的 YAML**——用户可能拼错字段名、给错类型、甚至塞进意外内容。`z.object` 会在 apply 之前把这一切挡住：未知字段被忽略或报错、类型不对直接拒绝、缺省字段补默认值。也就是说，**你在 `apply` 里永远拿到一份"干净"的配置**，可以放心用。反过来，如果跳过 `Config` 直接读 `config.greeting`，一旦用户没配，你的代码就崩在运行时——而 `Config` 会把错误提前到加载期，报错信息也更友好。

1. `ctx.tools.register(defineTool({...}))` 注册模型工具。`defineTool` 是官方 `@deepseek-ai/dsh-tools` 提供的工厂函数，字段含义：
   - `name`：工具名（模型调用名），**避免与内置工具冲突**（`read`/`write`/`edit`/`glob`/`grep`/`pwsh`/`todo_write` 等）；
   - `description`：给模型的说明，写清"何时用、怎么用"——描述越具体，模型越会正确调用；
   - `parameters`：参数 schema（JSON Schema 风格，下一章细讲）；
   - `output.schema` + `output.render`：返回值规范 + 展示渲染；
   - `execute(args, exec)`：工具实现，返回规范值；
   - `presentCall`：调用记录在 UI 上的展示卡片。
2. `ctx.effect(() => ctx.systemPrompt.section({...}), "hello.section()")` 注入提示词段落。`ctx.effect` 是生命周期原语：插件卸载时，这段注册自动清理。第二个参数是标签，便于排查。

## 5. 安装到本地 profile 并验证

### 5.1 语法自检（发布前随时可做）

```powershell
node --check lib\index.js
```

```bash
node --check lib/index.js
```

> 沙箱/CI 环境里 `node --test` 可能因为子进程被拦截而报 EPERM，此时改用"主模块方式"直接跑测试文件，详见 [08-常见问题](08-常见问题.md)。

**给 hello 插件补一个最小测试（养成好习惯）：** 虽然本章的插件很简单，但从一开始就把"纯逻辑可单测"的纪律立起来：把问候语拼接这类纯函数抽到 `lib/greet.js`，然后写 `test/greet.test.mjs` 用 `node:test` 直接测。07 章拆解的三个真实插件全部遵循这个模式——`lib/*.js` 零 DSH/Cordis 依赖、可独立单测，`lib/index.js` 只做接线。这一步虽然现在看起来“小题大做”，但它会在你写第二个、第三个插件时省下大量调试时间——纯函数测起来快、定位准，是性价比最高的测试投资。

### 5.2 装进 profile

用本地路径安装（开发期标准姿势，等价于 `pnpm add <路径>` + 自动 reconcile bundles 列表）：

```powershell
# PowerShell（Windows 路径用反斜杠）
dsh plugin --profile dev add D:\dev\hello-plugin
```

```bash
# bash
dsh plugin --profile dev add ~/dev/hello-plugin
```

### 5.3 验证三步走

**① 组合树里有没有它：**

```powershell
dsh --profile dev --dump-config | Select-String -Pattern "hello"
```

```bash
dsh --profile dev --dump-config | grep hello
```

**② 重启后跑一次会话，让模型调用工具：**

```powershell
dsh --profile dev "调用 hello 工具，向'新同学'打个招呼"
```

```bash
dsh --profile dev "调用 hello 工具，向'新同学'打个招呼"
```

**③ 看结果：** 模型应返回形如 `你好，我是第一个 DSH 插件！ 新同学（工作区：...）` 的消息，且工作区路径与运行命令的目录一致——工具真的跑起来了。

**预期中间过程（帮你判断故障在哪一步）：** 第 ② 步执行后，模型应当先"看到"工具列表里有 `hello`（来自组合树 + 提示词段落），然后决定调用它，传入 `name` 参数，`execute` 执行并返回规范值，`render` 把规范值渲染成界面文本，模型把结果组织进回答。如果模型直接说"我没有 hello 工具"，回到第 ① 步查组合树与 `id`/`name` 一致性；如果模型调用了但结果怪怪的，看 `execute` 返回的对象是否匹配 `output.schema`。

### 5.4 调配置试试

改 `cordis.patch.yml` 里的 `greeting`，重启后再问一次，问候语会跟着变。这验证了 `config` → `Config` → 工具行为的完整链路。你也可以顺便验证 `inject` 声明的作用：把 `inject` 里的 `systemPrompt` 删掉再启动，`ctx.systemPrompt` 会是 undefined，插件会报错——宿主就是这么保证"依赖就绪才 apply"的。

## 6. 常见新手错误（提前排雷）

**排雷的正确姿势：** 写完三件套先别急着装，把下表从头扫一遍——绝大多数错误发生在"文件之间的契约"上（id 对不上 name、漏了 bundle 声明、peer 放错位置），而不是代码本身。扫完再装，一次成功率会高很多。



| 错误 | 现象 | 修法 |
| --- | --- | --- |
| `id` 与 `name` 不一致 | 插件不加载或加载报错 | 让 `cordis.patch.yml` 的 `id` = `lib/index.js` 的 `name` |
| 漏写 `dsh.bundle.patch` | `dsh plugin add` 后不生效，dump 里没有 | 补上 `"dsh": { "bundle": { "patch": "./cordis.patch.yml" } }` |
| 官方包放进 dependencies | 装了两份运行时，行为诡异 | 一律放 peerDependencies |
| 忘了 `type: "module"` | import/export 语法报错 | 补 `"type": "module"` |
| 装完不重启 | 模型调不到新工具 | 重启 DSH |
| `execute` 返回自由文本 | 输出不符合 output.schema，展示异常 | 返回规范值对象 |
| `inject` 漏声明服务却使用 | `ctx.xxx` 是 undefined，运行时报错 | 用哪个服务就声明哪个（tools/systemPrompt/fs/agents…） |

这些错误里，**`id`/`name` 不一致**和**漏 `dsh.bundle.patch`** 是最隐蔽的两种：前者插件加载器会注册失败，后者 `dsh plugin add` 根本不知道这是个组合包。写完后把第 7 节的检查清单从头过一遍，能挡掉 80% 的新手坑。

## 7. 新手插件检查清单

- [ ] `package.json` 含 `dsh.bundle.patch` 与 `publishConfig.access: public`
- [ ] 官方 `@deepseek-ai/*` 全部在 peerDependencies
- [ ] `cordis.patch.yml` 用 `insert` 追加组合行，`id` 与插件 `name` 一致
- [ ] `lib/index.js` 导出 `{ name, inject, Config, apply }`
- [ ] `node --check` 通过；`dsh plugin add <路径>` 成功
- [ ] `--dump-config` 能看到组合行；会话里模型能调用 `hello`
- [ ] 验证过 `config` 改动会反映到工具行为
