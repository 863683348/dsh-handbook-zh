# 05 · 工具开发进阶：schema、文件系统、提示词与生命周期

> 一句话总结：生产级插件 = 严谨的 JSON Schema（参数与输出）+ 安全的 `ctx.fs` 文件访问（含工作区 containment 校验）+ 恰到好处的提示词段落 + 可清理的生命周期管理；本章用真实插件 `dsh-plugin-focus` 的写法讲透这四件事，并给出多工具插件的组织方式。

## 1. defineTool 全字段

从 [04-写第一个插件](04-写第一个插件.md) 我们知道工具通过 `ctx.tools.register(defineTool({...}))` 注册。`defineTool` 的核心字段：

| 字段 | 类型 | 作用 |
| --- | --- | --- |
| `name` | string | 工具名，模型调用时用；**避免与内置工具冲突**（`read`/`write`/`edit`/`glob`/`grep`/`pwsh`/`todo_write` 等） |
| `description` | string | 给模型看的说明：何时用、怎么用、有什么副作用 |
| `parameters` | object | 参数 schema（JSON Schema 风格的扁平字段描述） |
| `output.schema` | JSON Schema | 返回值的规范 schema（`type: "object"` + `properties`） |
| `output.render` | fn | 把规范值渲染成界面文本：`(_args, value) => [{ type: "text", text }]` |
| `execute(args, exec)` | async fn | 工具实现，返回**规范值**（必须符合 output.schema） |
| `presentCall` | fn | 调用记录在 UI 上的展示卡片 |

**几个容易忽略的设计原则：**

- **description 是"模型的说明书"**：写清楚"什么场景调用、参数怎么填、有没有副作用"。模型每次调用前都会读它，写得好，模型就调得准；写"提供 focus 功能"这种废话，模型基本不会主动用；
- **name 是"公共 API"**：一旦发布，改名会让旧会话/其他插件失效。命名用短横线或下划线小写，避免与内置工具撞名；
- **presentCall 决定"人看到的调用记录"**：`card`/`title`/`kind`/`rawInput` 四个字段控制 UI 展示，`rawInput` 是原始参数。

**推荐的开发顺序是 schema 先行**：先写 `parameters` 和 `output.schema`（这就是接口契约），再写 `execute` 的实现，最后补 `render` 和 `presentCall`。顺序反过来的后果是：实现写完了才发现返回值没法表达、参数漏了字段，被迫返工。三个官方插件（focus/recipe/gov）都是先有清晰的 schema 再有实现——你在 07 章会看到它们的 schema 如何精确到每个字段的 `required`。

## 2. parameters：扁平字段式 JSON Schema

DSH 模型的工具参数用 JSON Schema 描述。官方插件（如 focus、recipe、gov）的写法是**扁平字段式**：每个字段一个键，值是该字段的约束：

```js
parameters: {
  action: {
    type: "string",
    required: true,
    enum: ["set", "get", "append", "clear"],
    description: "对专注板做什么操作。",
  },
  note: {
    type: "string",
    description: "笔记内容；set / append 必填，get / clear 忽略。",
  },
}
```

常用约束键：

| 键 | 说明 | 例子 |
| --- | --- | --- |
| `type` | 字段类型 | `"string"`、`"integer"`、`"boolean"`、`"array"` |
| `required` | 是否必填 | `true`（必填） |
| `enum` | 枚举取值 | `["set", "get", "append", "clear"]` |
| `description` | 给模型的字段说明 | 写清楚何时必填、何时忽略 |
| `items` | 数组元素类型 | `items: { type: "string" }` |

**为什么是扁平字段式？** 因为对模型来说，扁平的、一眼能数清的参数表比嵌套的复杂结构更容易正确填充。DSH 工具设计的通用建议：

1. **动作收敛为 `enum`**：focus 的 `action`、recipe 的 `action`、gov 的 `action` 全都是枚举——枚举直接告诉模型"只能选这几个"，错误率断崖式下降；
2. **字段越少越好**：能省则省，可选的字段写明"何时忽略"；
3. **required 只标真正必填的**：标多了模型会为了凑参数而胡填。

## 3. output.schema + render：让返回值"规范且好看"

工具返回的必须是**规范值**（canonical value）——即符合 `output.schema` 的对象，而不是自由文本。规范值的好处：后续环节（审计、UI、其他工具）可以结构化地消费它。

```js
output: {
  schema: {
    type: "object",
    additionalProperties: false,
    required: true,
    properties: {
      action: { type: "string", required: true },
      path: { type: "string", required: true },
      entries: { type: "integer", required: true },
      changed: { type: "boolean", required: true },
      board: { type: "string" },
    },
  },
  render: (_args, value) => {
    const head = "Focus " + value.action + ": " + value.entries + " 条, " + (value.changed ? "已变更" : "未变更") + " — " + value.path;
    const lines = [head];
    if (value.board !== undefined) lines.push("", value.board);
    return [{ type: "text", text: lines.join("
") }];
  },
}
```

三个要点：

- **`additionalProperties: false`**：返回值里不允许 schema 之外的字段，强制规范。漏字段会校验失败，多字段也会——**schema 就是契约**；
- **顶层 `required: true`**：对象本身必填（不是每个属性都必填）；属性级 `required: true` 才是该属性必填；
- **render 与 schema 分离**：schema 管"数据是什么"，render 管"给人看什么"。render 返回消息块数组（如 `[{ type: "text", text }]`），可以拼多行、加空行、做摘要——注意 render 只是展示，**不要用它承载只有模型才需要的结构化信息**。

## 4. execute 与 exec 上下文

`execute(args, exec)` 里能拿到什么？看官方插件 focus 的实际用法：

```js
execute: async (args, exec) => {
  const cwd = exec.agent?.session?.header?.cwd; // 会话工作区！
  const signal = exec.signal;                   // 取消信号
  // ... 用 cwd 定位文件，返回规范值
  return { action, path, entries, changed, archived };
}
```

要点：

- **`exec.agent.session.header.cwd` 是会话工作区**——"文件放哪"都以它为基准，绝不要写死绝对路径；
- `exec.signal`：调用被取消时置为 aborted，长任务（大文件、循环、网络）要响应它，否则取消后还在干活；
- 抛 `Error` 即工具失败，模型会看到错误信息——**错误消息要写人话**（"focus: note 是必填的"比 "undefined is not a function" 有用一百倍）；
- 返回对象必须匹配 `output.schema`，这是运行时校验的硬约束。

## 5. ctx.fs：文件读写与工作区 containment

**插件读写文件必须走宿主 `ctx.fs` 服务**，不要直接 `node:fs`。常用方法（以 focus 源码为证）：

| 方法 | 作用 |
| --- | --- |
| `ctx.fs.resolve(path, { cwd, signal })` | 相对 `cwd` 解析出目标 |
| `ctx.fs.contains(target, other)` | 判断 `other` 是否在 `target` 之内（containment 校验） |
| `ctx.fs.stat(target, signal)` | 取文件信息；不存在返回 `undefined` |
| `ctx.fs.readText(target, signal)` | 读文本 |
| `ctx.fs.writeText(target, content, undefined, signal)` | 写文本 |
| `ctx.fs.processPath(target)` | 把目标转成展示用路径 |

**工作区 containment 是安全底线**：插件配置里出现的路径（如专注板文件）必须是"相对会话工作区的路径"，并且**永远不能逃逸工作区**。官方插件的标准写法是"解析后校验"：

```js
async function resolveTarget(ctx, file, cwd, signal) {
  // 1) 先解析：相对 cwd 的文件路径 → 绝对目标
  const target = await ctx.fs.resolve(file, cwd !== undefined ? { cwd, signal } : { signal });
  if (cwd !== undefined) {
    // 2) 再校验：目标必须在工作区之内，否则直接拒绝
    const cwdTarget = await ctx.fs.resolve(".", { cwd, signal });
    if (!ctx.fs.contains(cwdTarget, target)) {
      throw new Error('configured file "' + file + '" escapes the session workspace');
    }
  }
  return target;
}
```

**为什么这么重要？** 插件运行在 Agent 进程里，若允许任意路径，一个被诱导的插件配置就能让 Agent 读写工作区之外的文件（比如用户主目录里的敏感文件）。所以：**所有**解析出的路径都要过 `ctx.fs.contains` 这道闸。dsh-plugin-focus 里板子文件配置成工作区外路径会"fail loud"（直接报错），这是刻意设计——**宁可报错，不可悄悄越界**。

**"写文件先 stat 再 readText 再 writeText"的三步模式**（focus 的 loadBoard/appendArchive 都是这个套路）：`stat` 判断存在性 → `readText` 读旧内容 → `writeText` 写新内容。文件不存在时 `stat` 返回 `undefined`，据此决定是"空内容"还是"读旧追加"。

focus 的 appendArchive 就是一个完整示范：`stat` 目标归档文件 → 不存在则以空串开始 → 存在则 `readText` 读旧内容 → 拼接新块 → `writeText` 写回。注意 append 类操作**必须读-改-写三步**，而不是只 `writeText`——否则会把旧内容覆盖掉。

## 6. ctx.systemPrompt.section：注入提示词

教模型"什么时候用什么工具、别干什么"，靠提示词段落。注册方式：

```js
ctx.effect(() => ctx.systemPrompt.section({
  name: "focus:instructions",   // 段落名
  order: 5,                     // 顺序（persona 为 0，升序排列）
  text: "The focus tool maintains a durable focus board...",
}), "focus.section()");
```

- `name`：段落唯一名，惯例是 `<插件名>:instructions` 之类的命名空间式；
- `order` 控制段落先后（如 persona 是 0，插件段落常用 5，多个插件按数字排队）；
- 段落文本面向模型，写"何时用、怎么用、注意事项"——focus 的段落就详细教了"任务开始 set、工作中 append、上下文压缩后 get、任务结束 clear"的完整用法；
- 用 `ctx.effect` 包裹：插件卸载时段落自动移除，不留垃圾。

**段落与 description 的分工**：`description` 是"这个工具是什么"，段落是"整套工具的用法规范与触发时机"。工具少时段落可以简单（04 章 hello 只有一句话），工具多、行为复杂时段落才是主角（focus、gov 都是）。

## 7. ctx.effect 与事件钩子：生命周期管理

`ctx.effect(fn, label)` 是 Cordis 的生命周期原语：`fn` 里注册的一切（监听器、段落、定时器）在插件作用域结束时自动清理。注册事件钩子的标准姿势：

```js
// 工具执行前拦截（dsh-gov 的策略门禁）
ctx.on("tools/pre-execute", async (exec, next) => {
  // 返回 { kind: "deny" | "ask", reason } 直接裁决；否则放行 next()
  return next();
});

// 工具执行后观察结果（dsh-gov 的审计）
ctx.on("tools/result", (exec, result) => {
  // result.isError 标记成败
});

// 每轮 Agent 步进前（dsh-gov 的配额计量、dsh-plugin-focus 的板子注入）
ctx.on("agent/pre-step", async ({ agent, turn, step, signal }, next) => {
  const decision = await next();
  if (decision.kind === "reject") return decision;
  // 可以往模型上下文里追加 plugin snapshot 消息
  return decision;
});
```

事件钩子的三种形态：

| 形态 | 签名 | 用途 |
| --- | --- | --- |
| 拦截型 | `(payload, next)` 返回 next() 或拒绝决策 | `tools/pre-execute` 门禁、`agent/pre-step` 注入 |
| 观察型 | `(payload, result)` 无返回值 | `tools/result` 审计 |
| 纯注册 | 普通 `ctx.on` | 监听事件做记录 |

**waterfall（级联）监听与普通监听的区别**：像 `agent/pre-step` 这样带 `next` 参数的监听器是 waterfall 形态——多个插件都监听同一事件时，它们按注册顺序串成一个链条，每个监听器都要决定"放行（调用 next）还是裁决（返回自己的决策）"。focus 的板子注入、gov 的配额计量都挂在这个链条上，所以它们都必须 `await next()` 先让链条走完，再决定追加还是覆盖。而 `tools/result` 这类观察型监听没有 `next`，只是"看一眼记一笔"，顺序无所谓。**写钩子前先想清楚：我是要拦截裁决，还是只看记录？** 这决定了你该用哪种形态。

`inject` 数组声明依赖（如 `["tools", "fs", "systemPrompt", "agents", "tokenMeter"]`），宿主保证这些服务就绪后才 `apply`。以官方包为参考：`dsh-gov` 就 `inject` 了 `tokenMeter` 来做 token 配额。**可用的事件与服务清单以官方文档为准**——本章列的是真实插件里验证过的常用项。

## 8. 多工具插件：一个插件注册多个工具

一个插件可以注册任意多个工具（以及多个段落、多个钩子）。组织方式：

```js
function apply(ctx, config) {
  ctx.tools.register(defineTool({ name: "tool_a", /* ... */ }));
  ctx.tools.register(defineTool({ name: "tool_b", /* ... */ }));

  ctx.effect(() => ctx.systemPrompt.section({ /* section 1 */ }), "plugin.section1()");
  ctx.effect(() => ctx.systemPrompt.section({ /* section 2 */ }), "plugin.section2()");
  // 所有注册都在 apply 里完成，Cordis scope 统一清理
}
```

dsh-gov 就是多工具插件：一个 `gov` 工具 + `tools/pre-execute`、`tools/result`、`agent/pre-step` 三个钩子 + 提示词段落。工具多时的组织建议：

1. **schema 常量化**：把每个工具的 `parameters`、`output.schema` 提成模块级常量，`apply` 只做装配，可读性大幅提升；
2. **共享辅助函数**：多个工具都要用"解析 + containment 校验"就把 `resolveTarget` 这类函数提到文件级（focus 就是这么干的）；
3. **一个工具一个关注点**：宁可拆两个工具，不要把"查询"和"修改"塞进一个 `action` 枚举里（gov 的 9 个 action 已经是上限了，再复杂就该拆工具）。

**三个常见误区（对照检查）：**

1. **"`render` 就是给模型看的"**——不完全对。`render` 决定的是界面/日志里的展示文本；模型看到的工具结果是规范值经展示层处理后的样子，但**结构化信息必须走 schema 字段**，别塞进 render 的字符串里让模型去解析；
2. **"`ctx.fs` 只是方便，我可以直接用 `node:fs`"**——不行。宿主 `ctx.fs` 负责路径沙箱、containment、权限与审计，绕开它等于把工作区安全模型拆了；
3. **"工具越全越好"**——不是。工具是模型要读的 API 面，太多太杂会让模型选择困难。宁可少而精，把描述写透。

## 9. 进阶最佳实践清单

- [ ] `parameters` 用扁平 JSON Schema，动作收敛为 `enum`，字段写清"何时必填"
- [ ] 返回值是规范值（`output.schema` 约束），`render` 负责展示
- [ ] 用 `exec.agent.session.header.cwd` 定位工作区，不写死绝对路径
- [ ] 文件读写走 `ctx.fs`，且解析后过 `ctx.fs.contains` containment 校验
- [ ] 提示词段落用 `ctx.effect` 包裹，设置 `order`
- [ ] 事件钩子返回规范决策（`next()` / `{kind: "deny"}`），长任务响应 `signal`
- [ ] 纯逻辑（无 DSH/Cordis 依赖）抽到独立模块，便于单测
- [ ] 错误消息写人话，不抛 undefined 之类的裸异常
