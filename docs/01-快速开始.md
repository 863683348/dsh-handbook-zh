# 01 · 快速开始：30 分钟把 DeepSeek Harness 跑起来

> 一句话总结：DeepSeek Harness（DSH）是一个"用插件组合出来的 Agent 运行时"，你只需要安装一个 `dsh` 命令，就能启动 Web 界面、跑无头会话、管理插件——本章带你完成第一次完整的上手，建立"命令 → profile → 工具 → workspace"的全局心智。

## 本章目标

读完本章并照做，你将：

- 安装并验证 `dsh` 命令；
- 启动一次 Web 会话（`dsh web`）并发出第一个任务；
- 用 `headless` 模式跑一个一次性的持久化会话；
- 记住 DSH 最常用的入口命令，并能说出 workspace 与 $DSH_HOME 的含义。

## 1. 先建立一个整体印象

DeepSeek Harness 的定位可以概括成一句话：**一个以插件为积木的 Agent 运行时**。它不是一个"聊天软件"，也不是一个"代码生成器"，而是一个平台——你（或社区）用插件给它拼出各种能力，模型在平台上调用这些能力干活。官方口号"一切皆插件"说的就是这个：工具是插件、提示词是插件、界面面板是插件、甚至 Agent 的治理规则也是插件。

命令行工具 `dsh` 是进入这个平台的钥匙。它本身很"薄"，主要做三件事：

| dsh 的职责 | 说明 |
| --- | --- |
| 启动 profile | `dsh --profile <name>` 把某个 profile 的组合配置加载起来 |
| 管理插件 | `dsh plugin` 在 profile 里增删插件（转发给 pnpm） |
| 提供别名 | `dsh web` 就是 `--profile web` 的别名 |

你不需要先精通插件才能用 DSH——就像不需要会修车才能开车。本章先把车开起来。

## 2. 准备工作

你需要一台能跑 Node.js 的电脑（Windows / macOS / Linux 均可）。DSH 本体是一个 npm 包，命令行工具叫 `dsh`，所以唯一硬性依赖是 Node.js 与 npm。建议使用当前 LTS 版本的 Node.js，具体版本要求以官方文档为准。

```powershell
# PowerShell：查看 node 与 npm 版本
node --version
npm --version
```

```bash
# bash（macOS / Linux / WSL）
node --version
npm --version
```

另外请准备好一个你常用的终端：Windows 上用 PowerShell 或 Windows Terminal，macOS/Linux 上用任意 shell。本书所有命令都给出双写法，绝大多数 `dsh` 命令在两个 shell 下完全一致，只有涉及路径、引号、环境变量时才需要区分——遇到不一致的地方，[08-常见问题](08-常见问题.md) 有专门的对照表。

> 国内网络提示：npm 默认走官方源，安装慢或失败时可以临时切换镜像源（如 `npm config set registry https://registry.npmmirror.com`）。这属于通用 npm 知识，具体以你的网络环境为准。

## 3. 安装 dsh

`dsh` 是 DeepSeek Harness 中用于启动 profile 的命令，随 npm 包 `@deepseek-ai/dsh` 分发。全局安装它：

```powershell
npm install -g @deepseek-ai/dsh
```

```bash
npm install -g @deepseek-ai/dsh
```

安装完成后验证：

```powershell
dsh --version
dsh --help
```

```bash
dsh --version
dsh --help
```

- `dsh --version` 应打印版本号（本书写作时官方版本为 0.1.0-rc.6，以你安装到的版本为准）；
- `dsh --help` 打印**启动器自己的**帮助——注意它只包含启动器 flag，不包含某个具体应用（如 Web 应用）的 flag。这个区别很关键：`dsh --help` 与 `dsh --profile web --help` 打印的是两份不同的帮助，下一章会专门讲。

> Windows 提示：如果 `dsh` 提示"不是内部或外部命令"，多半是 npm 全局 bin 目录不在 PATH 里。执行 `npm prefix -g` 找到全局目录，把它的 bin 子目录加进 PATH 后重开终端。

需要升级时：

```powershell
npm update -g @deepseek-ai/dsh
```

```bash
npm update -g @deepseek-ai/dsh
```

卸载则 `npm uninstall -g @deepseek-ai/dsh`（一般用不到，先知道有这回事）。

## 4. 两个关键概念：$DSH_HOME 与 workspace

在跑第一条命令之前，先建立两个心智模型，它们贯穿全书。

**$DSH_HOME——DSH 的家。** profile 目录、全局配置（home 级 `cordis.patch.yml`）、会话数据都存在这里。未设置时默认是用户主目录下的 `.dsh`：

```powershell
# PowerShell：查看默认家目录
echo "$env:USERPROFILE\.dsh"
```

```bash
# bash
echo "$HOME/.dsh"
```

第一次启动后你可以进去逛一逛，会看到 `profiles/` 目录（每个 profile 一个子目录）。profile 结构在 [02-理解-profile](02-理解-profile.md) 详细拆解。

**workspace——Agent 干活的工作区。** **运行 `dsh` 命令时所在的目录就是默认 workspace 根**。也就是说，你在哪个目录启动 DSH，Agent 默认就在哪个目录里读文件、写文件、跑命令。想让它处理某个项目，就先 `cd` 进那个项目再启动。

> 为什么强调 workspace？因为"Agent 只在自己的工作区里动手"是 DSH 的安全模型之一：插件写的文件、跑的命令都默认圈定在 workspace 里。第 05 章讲 `ctx.fs` 的 containment 校验时你会再次遇到它。一个直观的验证方法：在空目录 A 启动 `dsh web` 让模型建文件，再换到空目录 B 启动——模型不会"记得"A 里的文件，因为 workspace 不同、会话也不同。

## 5. 第一次启动：dsh web

`dsh web` 是 `--profile web` 的别名，启动带图形界面的 Web 版 DSH。首次使用时，`web` profile 会**自动从随附模板初始化**——你不需要手动建目录、不需要写任何配置：

```powershell
# 在你想作为 workspace 的目录里启动（PowerShell）
cd D:\projects\my-first-dsh
dsh web
```

```bash
# bash
cd ~/projects/my-first-dsh
dsh web
```

启动过程你会看到：首次初始化 profile 的日志 → 本地服务启动 → 打印访问地址（通常形如 `http://127.0.0.1:3000` 或类似，**以终端实际输出为准**）。用浏览器打开，就是 DSH 的 Web 界面：左边是会话列表与工具区，中间是对话区，你可以把它理解成一个"自带文件系统访问和命令执行能力的 AI 助手界面"。

在输入框里发第一个任务，比如：

> 帮我在当前工作区创建一个 README.md，说明这个目录的用途。

你会看到模型先规划、再调用内置工具（读写文件、执行命令）逐步完成，最后汇报结果。打开文件管理器确认 `README.md` 真的被创建在了**你启动命令的那个目录**——这验证了 workspace 的概念：它没有跑偏去别的地方。

Web 应用自己的 flag 要写在启动器 flag 之后——启动器只解析自己的 flag，其余内容全部交给 profile 应用：

```powershell
dsh --profile web --port 8080
```

```bash
dsh --profile web --port 8080
```

这里 `--port 8080` 属于 Web 应用而非启动器。同理，`dsh --profile web --help` 打印的是 Web 应用的帮助，而 `dsh --help` 才是启动器的帮助。这个"flag 分家"的规则在 02 章有更完整的解释。

**5.1 一次完整的 Web 会话实录（预演）**

第一次用 Web 界面时，把下面的过程在脑子里过一遍，实际体验就不会慌：

1. 你在工作区目录里执行 `dsh web`，终端打印地址，浏览器打开界面；
2. 你发出任务："列出当前目录的文件，并告诉我每个文件的用途猜测"；
3. 模型先调用内置的目录/文件工具（如列目录、读文件）收集事实；
4. 模型基于读到的内容组织回答，必要时再补读一两个文件确认；
5. 你追问"把最重要的那个文件改成英文版"——模型继续在同一会话上下文里执行修改；
6. 你随时可以新建会话（清空上下文）或切换工作区——记住 workspace 由启动命令的目录决定。

注意第 5 步：**同一个会话里上下文是连续的**，模型记得之前读过什么。而 headless 每次都是全新会话，这正是两者使用方式上的根本差异。

## 6. 第二次启动：headless 无头会话

不需要界面、只想要一个最终答案时，用 `headless` profile：

```powershell
dsh --profile headless "写一段 200 字左右的 Python 代码，读取当前目录下所有 .md 文件的文件名并打印"
```

```bash
dsh --profile headless "写一段 200 字左右的 Python 代码，读取当前目录下所有 .md 文件的文件名并打印"
```

`dsh --profile headless "job"` 会**运行一个全新的持久化会话**（persistent session），完成作业后**打印最终答案并退出**。它和 web 一样首次使用自动初始化。三个值得注意的点：

1. **全新**：每次调用都开一个全新会话，不会带上上次对话的上下文（除非通过持久化机制，如插件写的工作区文件）；
2. **持久化**：会话本身是持久化的（有会话 ID、可恢复），不是无状态的一次性调用；
3. **打印答案退出**：适合脚本化——你可以把它嵌进批处理、CI、定时任务里，当成一个"带 Agent 的 CLI"用。

> 引号注意：PowerShell 与 bash 都要求把整个任务文本用引号包起来。如果任务文本里含有双引号，PowerShell 建议外层用单引号，bash 则注意转义，详见 [08-常见问题](08-常见问题.md)。

**6.1 web 还是 headless？一张表说清楚**

| 维度 | `dsh web` | `dsh --profile headless "任务"` |
| --- | --- | --- |
| 界面 | 浏览器图形界面 | 无界面，纯命令行 |
| 会话 | 可多会话、可追问、上下文连续 | 每次全新会话，打印答案退出 |
| 适合 | 交互式工作、需要反复确认 | 一次性任务、脚本/CI/批处理 |
| 初始化 | 首次自动 | 首次自动 |
| 典型姿势 | 人坐在电脑前 | 人不在场，或嵌入自动化 |

> 简单记：**人在就 web，人不在就 headless**。两者共享同一个 profile 体系（headless 对应 `headless` profile），装在同一 profile 里的插件两边都能用——插件知识从 03 章开始。

## 7. 常用入口命令速查表

| 命令 | 作用 | 什么时候用 |
| --- | --- | --- |
| `dsh --version` / `dsh --help` | 版本 / 启动器帮助 | 环境自检、忘了 flag 时 |
| `dsh web` | 启动 Web 版 | 日常交互式使用 |
| `dsh --profile web --port 8080` | 指定端口启动 Web 版 | 默认端口被占用时 |
| `dsh --profile headless "任务"` | 跑一次性无头会话 | 脚本化、批量化、CI |
| `dsh --profile <name>` | 启动任意 profile | 用自定义 profile 时 |
| `dsh plugin --profile <name> <pnpm args>` | 管理该 profile 的插件 | 装/卸插件（03 章） |
| `dsh --dump-config` | 打印组合后的配置树 | 排查配置问题（02 章） |

## 8. 第一个完整任务示例

把前面的概念串起来，完整走一遍"建目录 → 启动 headless → 拿到产物 → 验证"：

```powershell
# PowerShell
mkdir D:\scratch\dsh-demo
cd D:\scratch\dsh-demo
dsh --profile headless "创建 hello.txt，内容为 'Hello from DeepSeek Harness'，然后读取并打印它"
Get-Content hello.txt
```

```bash
# bash
mkdir -p ~/scratch/dsh-demo
cd ~/scratch/dsh-demo
dsh --profile headless "创建 hello.txt，内容为 'Hello from DeepSeek Harness'，然后读取并打印它"
cat hello.txt
```

**预期过程与结果：**

1. headless 会话在 workspace（即 `dsh-demo` 目录）里创建 `hello.txt`；
2. 模型读取该文件并打印内容；
3. 会话打印最终答案后退出；
4. 你手动 `cat` / `Get-Content` 验证文件确实存在于当前目录。

这就是 DSH 的最小闭环：**命令 → profile → Agent 工具 → workspace 产物**。注意观察：所有文件操作都发生在 `dsh-demo` 里，因为启动命令的目录就是 workspace 根。

## 9. 常见误解（先打个预防针）

| 误解 | 事实 |
| --- | --- |
| "DSH 是另一个 ChatGPT 网页" | 它是有文件系统、命令执行、插件体系的 Agent 运行时，Web 只是入口之一 |
| "`dsh web` 要手动配置" | web / headless 首次使用自动初始化，零配置 |
| "`dsh --help` 能看到全部参数" | 那只是启动器帮助；应用参数要看 `dsh --profile web --help` |
| "模型在哪都能写文件" | 默认只在自己的 workspace 里动手，路径解析受控 |
