# 03 · 插件入门：找插件、装插件、验证生效

> 一句话总结：DSH 的官方口号是"一切皆插件"，插件生态爆发式增长（上线 72 小时即超过 4300 个）；本章教你在三个入口里找到想要的插件，用 `dsh plugin` 装进指定 profile，再用 `--dump-config` 验证它真的生效。

## 1. 插件生态速览

在 DSH 里，**插件（plugin）就是一个可安装的"组合包"**：它带着自己的 patch 层（`cordis.patch.yml`）和实现代码（Cordis 插件），安装进 profile 后自动参与第 02 章讲的配置叠加。生态现状：

- **"一切皆插件"**是官方口号：工具、提示词、界面面板、生命周期钩子……都是插件；
- 生态增长极快：DeepSeek Harness 上线 72 小时插件生态即超过 **4300+**；
- `awesome-dsh-plugin` 是官方精选列表，`data/plugins` 目录已有 **1500+** 条目（持续增长中）。

一个插件通常给 Agent 带来三样东西之一（或组合）：

| 插件能力 | 说明 | 例子 |
| --- | --- | --- |
| 模型工具（tool） | 给 Agent 新增可调用的函数 | `focus` 专注板、`recipe` 配方 |
| 提示词段落（section） | 注入使用指引，改变模型行为 | `focus:instructions` |
| 生命周期钩子 / UI | 拦截事件、渲染面板 | dsh-gov 的门禁与审计、focus 的 Web 面板 |

**这套机制意味着什么？** 不妨把"装插件"想成给 Agent 加技能：装一个 `dsh-plugin-focus`，Agent 就多了一个"把目标钉在纸上、跨会话不忘"的能力；装 `dsh-recipe`，Agent 就多了一个"按场景批量推荐插件"的能力；装 `dsh-gov`，Agent 的所有工具调用就多了一道"权限检查 + 审计记录"。你不需要改任何核心代码——这正是"一切皆插件"的威力：**平台的能力边界，由插件生态决定，而不是由官方版本迭代决定**。装一个 `dsh-plugin-focus`，Agent 就多了一个"把目标钉在纸上、跨会话不忘"的能力；装 `dsh-gov`，Agent 的所有工具调用就多了一道"权限检查 + 审计记录"。你不需要改任何核心代码，插件就是一切。

## 2. 三个找插件的入口

**入口 A：GitHub topic**

GitHub 上打了 `dsh-plugin` topic 的仓库就是插件（`deepseek-harness`、`cordis` 等是相关标签）。直接访问：

```text
https://github.com/topics/dsh-plugin
```

在页面里可以按"最近更新""星数"排序，也可以用主题页的搜索框叠加关键词（如 `dsh-plugin memory`）。这是**发现新插件**最好的入口——npm 里只有发布了的包，而 GitHub 上有正在开发中的。

**入口 B：npm registry**

包名通常带 `dsh-plugin` 前缀。在终端里搜：

```powershell
npm search dsh-plugin
```

```bash
npm search dsh-plugin
```

输出会列出包名、描述、作者。想过滤出真正可安装的，可以再精确一点：`npm search dsh-plugin focus`、`npm search dsh-plugin governance`。注意：**npm 搜得到不等于维护活跃**，安装前看一眼包的更新时间与 README。

**入口 C：awesome-dsh-plugin 精选列表**

```text
https://github.com/awesome-dsh-plugin/awesome-dsh-plugin
```

列表按分类组织（`tools`、`memory`、`notify`、`workflow`、`dev`、`fun` 等），每个条目指向一个插件仓库，README 由脚本从 `data/plugins` 生成（这个机制在第 06 章发布时还会用到）。**选插件先看这里**——能进精选列表的至少过了 CI 门槛（仓库 ≥1 天、≥10 commits、声明了 `dsh.bundle`）。

> 社区参考：作者 863683348 的插件家族覆盖了多种场景，可作为"一个插件应该长什么样"的标本：`dsh-plugin-focus`（专注板）、`dsh-recipe`（场景配方）、`dsh-gov`（治理套件）、`dsh-plugin-audit`、`dsh-feed`、`dsh-insight`、`dsh-trend-radar`、`dsh-plugin-guide` 等，均可在 GitHub / npm 搜索到。07 章会深入拆解其中三个。

## 3. 安装插件

插件按 profile 安装——**装进哪个 profile，只对那个 profile 生效**。语法：

```text
dsh plugin --profile <name> <pnpm args>
```

即 `dsh plugin` 会在 profile 目录里把后面的参数转发给 pnpm。最常见的两个操作是 `add` 与 `remove`。

从 npm 安装（包已发布）：

```powershell
dsh plugin --profile web add dsh-plugin-focus
```

```bash
dsh plugin --profile web add dsh-plugin-focus
```

从本地目录安装（开发期，等价于 `pnpm add <路径>` 并自动 reconcile 组合包列表）：

```powershell
dsh plugin --profile web add D:\dev\dsh-plugin-focus
```

```bash
dsh plugin --profile dev add ~/dev/dsh-plugin-focus
```

安装完成后**重启 DSH**（退出正在运行的 `dsh web` / headless 会话再启动），插件才会被加载。为什么必须重启？因为 profile 的配置树在**启动时**组合，运行中的会话不会自动热加载。

> pnpm 参数都能透传，例如指定版本：`dsh plugin --profile web add dsh-plugin-focus@1.0.1`。更复杂的 pnpm 用法以官方文档为准。

**三种安装来源，什么时候用哪个？**

| 来源 | 命令 | 适用场景 |
| --- | --- | --- |
| npm 已发布包 | `dsh plugin --profile <name> add <包名>` | 日常使用、生产环境 |
| 本地目录 | `dsh plugin --profile <name> add <路径>` | 开发调试、未发布插件 |
| 指定版本 | `dsh plugin --profile <name> add <包名>@<版本>` | 锁定版本、回滚 |

开发期建议一律用本地目录安装：改代码 → 重启 → 验证，循环极快；等验证稳定了再走第 06 章的发布流程。

**装之前确认两件事：**

1. profile 存在吗？web / headless 首次使用自动初始化；自定义 profile 首次用 `dsh plugin` 创建；
2. 包名对吗？npm 包名与 GitHub 仓库名不一定相同（如仓库 `dsh-plugin-focus`，npm 包名也是 `dsh-plugin-focus`，但有的插件可能带 scope 或别名）——以包 README 里的安装命令为准。

## 4. 移除插件

```powershell
dsh plugin --profile web remove dsh-plugin-focus
```

```bash
dsh plugin --profile web remove dsh-plugin-focus
```

移除后同样需要重启。插件卸载会清理它注册的工具、提示词段落与生命周期钩子（Cordis scope 管理，详见第 05 章）——**不需要你手动去删配置**，`dsh plugin remove` 会自动 reconcile 组合包列表。

想观察"安装到底动了什么"？装完去 `$DSH_HOME/profiles/<name>/` 里看一眼：`package.json` 里多了该插件的依赖项，`dsh.profile` 的 bundles 列表里多了该组合包，`node_modules/` 里出现了它的安装产物。这三个变化，正是第 02 章"树外插件"的落地过程——**装一个插件 = 依赖声明 + 组合列表 + 代码落地**，三者缺一，插件就不会生效。

## 5. 验证插件真的生效了

装完别急着信，用两步验证。

**第一步：看配置树。** `--dump-config` 输出的是组合后的最终配置树，插件若生效，它的组合行（id、包名、config）一定在里面：

```powershell
dsh --profile web --dump-config | Select-String -Pattern "focus"
```

```bash
dsh --profile web --dump-config | grep focus
```

有输出 = patch 层生效；没输出 = 插件没进组合树，按第 02 章"改了配置为什么没生效"的顺序排查。输出里你会看到类似 `- id: focus`、`name: 'dsh-plugin-focus'` 以及它的 `config` 块——**这三样齐全，才说明 patch 真的被组合进去了**。如果只有 id 没有 config，多半是 patch 格式问题（比如 YAML 缩进错误），回去检查 `cordis.patch.yml`。

**第二步：在会话里让模型调用它。** 配置树生效只代表"组合完成"，还要验证"运行时可用"。启动 `dsh web`（或 headless），直接让模型用新工具：

> 用 focus 工具把当前任务的目标记下来。

如果模型能调用 `focus set` 并返回结果，插件就在运行时生效了。在 Web 界面的工具列表里通常也能看到新注册的工具——模型"看不见的插件"等于没装。

**5.1 一个完整的"安装 → 验证"实操演示**

把上面的步骤串成一段连贯操作，你照抄即可（假设目标 profile 是 `web`）：

```powershell
# 第 1 步：安装
dsh plugin --profile web add dsh-plugin-focus
# 第 2 步：确认进了组合树（应该看到包含 focus 的行）
dsh --profile web --dump-config | Select-String -Pattern "focus"
# 第 3 步：启动，让模型调用
dsh web
```

```bash
# 第 1 步：安装
dsh plugin --profile web add dsh-plugin-focus
# 第 2 步：确认进了组合树（应该看到包含 focus 的行）
dsh --profile web --dump-config | grep focus
# 第 3 步：启动，让模型调用
dsh web
```

第 3 步启动后在界面里发："用 focus 工具记下：当前目标是学习 DSH 插件开发。"然后观察：模型应调用 `focus set` 并返回包含路径与条目数的结果。这时再到工作区看看，会发现 `.dsh/focus.md` 文件——**配置生效（组合树）与运行生效（工具调用）两个证据都齐了**。

## 6. 插件管理命令速查表

| 命令 | 作用 | 备注 |
| --- | --- | --- |
| `dsh plugin --profile <name> add <pkg>` | 从 npm 安装插件到指定 profile | 装完重启 |
| `dsh plugin --profile <name> add <路径>` | 从本地目录安装（开发期） | 自动 reconcile bundles |
| `dsh plugin --profile <name> remove <pkg>` | 卸载插件 | 卸完重启 |
| `dsh plugin --profile <name> <其他 pnpm 参数>` | 其他 pnpm 操作（升级、查看等） | 以官方文档为准 |
| `dsh --profile <name> --dump-config` | 验证组合树里有没有该插件 | 排查第一现场 |

注意事项：

- profile 必须已存在（web/headless 自动初始化；自定义 profile 首次通过 `dsh plugin` 创建）；
- 装完/卸完都要重启 DSH 才生效；
- 内置组合包（`@deepseek-ai/dsh-base` 等）**不要**用 `dsh plugin` 去动，它们由 dsh 安装目录解析、随版本升级。

## 7. 装哪些？先看精选清单

不知道自己需要什么插件？三条参考路径：

1. **看 awesome-dsh-plugin 的分类**：按你的场景找分类（记忆、通知、工作流……）；
2. **用 `dsh-recipe` 的场景配方**：装 `dsh-recipe` 后直接让模型"给我配一套学术写作环境"，它会给出有序插件清单和安装命令（07 章详述）；
3. **看本仓库的精选推荐**：配套的 `starter/recommended-plugins.md` 按场景整理了经过验证的插件清单，适合新手起步。

**动手练习（10 分钟）：** ① 用 `dsh plugin --profile web add dsh-recipe` 装上场景配方插件；② `--dump-config` 确认组合行；③ 在会话里让模型 `recipe list`，看看内置的 10 个配方；④ 让模型 `recipe apply` 一个你感兴趣的配方，观察它返回的有序插件清单和安装命令；⑤ 最后 `dsh plugin --profile web remove dsh-recipe` 卸掉。这一圈走完，装、查、用、卸四个动作你都亲手做过了。

## 8. 常见问题速答

**问：装完插件重启后模型还是不调用它？** 先确认描述：工具的描述（description）是否说清了"何时用"？如果描述含糊（比如只说"提供 focus 功能"），模型不知道在什么场景调用。其次确认提示词段落有没有注入——第 05 章会讲怎么用 `ctx.systemPrompt.section` 教模型用工具。

**问：`dsh plugin add` 报 profile 不存在？** web / headless 首次使用才自动初始化；自定义 profile 第一次用 `dsh plugin` 创建。如果是自定义 profile，先执行一次 `dsh plugin --profile <name> add <任意包>` 让它初始化，再装目标插件（具体行为以官方文档为准）。

**问：同一插件能装到多个 profile 吗？** 能。插件按 profile 安装，互不干扰；同一插件在不同 profile 里可以有不同的 `config`（因为每个 profile 的 `cordis.patch.yml` 是独立的）。

**问：`npm search` 找不到某个插件？** 可能它还没发布（只在 GitHub 上）、名字不同（换过名或带 scope），或刚发布索引未更新。去它的 GitHub 仓库 README 看确切的安装命令。

**问：装了很多插件会不会拖慢启动？** 会有一点。每个插件都要参与配置组合与运行时加载，装得越多启动越慢、潜在冲突越多。建议：按 profile 划分职责（开发/生产分开），用不上的插件及时 remove，保持每个 profile"小而精"。这也正是 `dsh-recipe` 这类"场景配方"插件存在的意义——按需组装，而不是全装。
